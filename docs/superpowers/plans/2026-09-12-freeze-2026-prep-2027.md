# Plan: freeze the 2026 season, prepare the 2027 cycle

Decided with Wes 2026-09-12. Five independent PRs, each built in its own
worktree by a separate implementer, each squash-merged to `main` on its own.

## Global constraints (bind every task)

- Read `CLAUDE.md` at the repo root first. Its gotchas are binding: shared
  global scope (bare-name component references, defining script must be
  loaded on the page), `trackEvent` never `window.sendEvent`, `greens` shape
  is the contract, `.grg-press` needs `--grg-sh`, Worker degrades gracefully
  (missing secrets never break the static site or the share link), no
  em dashes in user-facing copy, `/api/city` returns aggregates plus the
  deliberate `camps` name+coords list and nothing else per camp.
- **Do NOT edit `CHANGELOG.md` or `APP_VERSION`.** The controller stamps
  both at integration time, once the PR number exists.
- **Do NOT commit anything under `dist/`.** Run `bun run scripts/build.js` to
  test locally, but `git restore dist` (or leave it unstaged) before
  committing. The controller rebuilds `dist/` at integration.
- Secrets: never write a secret value anywhere. Secret *names* only.
- `bun test` must pass. If you add Worker logic, add a `bun test` case using
  the existing `withMockFetch` helper pattern in `test/`.
- Any UI change must be verified against the real running app in a
  phone-sized viewport (390x667) via Playwright (`~/.claude/pw/browser.ts`
  with `bunx`, `HEADED` unset). Serve with `python3 -m http.server <PORT>`
  from the worktree root; use the port your dispatch assigns. Never look at
  a screenshot in the controller; describe what you saw in the report.
- One commit per task is ideal; a few is fine. Conventional, descriptive
  subject lines. Commit only in your worktree branch, never on `main`.
- Season rollover decision (Wes, 2026-09-12): each season gets a **new
  Google Sheet** and a fresh Apps Script deployment bound to it; the
  `SHEETS_WEBAPP_URL` secret is re-pointed. `SHEET_NAME` in `Code.gs`
  stays year-pinned (`'2026 Results'` today). The admin page therefore shows
  only the current season's sheet; previous seasons live in their own
  archived sheets.

## Task 2: Year-keyed question content

Goal: archive the 2026 question set so 2027 content edits never overwrite it,
and every consumer that has a year resolves the matching set. Zero behaviour
change for the live game today.

- `game-data.js`: wrap the current `SECTORS` array as
  `SECTORS_BY_YEAR = { 2026: <the array> }`. Export/attach (matching the
  file's existing isomorphic pattern for `window.SECTORS` and the Worker
  import) `SECTORS_BY_YEAR`, a `CURRENT_YEAR` = the max numeric key, and
  `sectorsForYear(year)`: returns the set for that exact year, else the set
  for the greatest key less than `year`, else the earliest set. `SECTORS`
  keeps pointing at the current-year set so all existing callers still work.
  Add a comment block explaining how to add a 2027 set (add a key, do not
  edit 2026; bump `STORAGE_VERSION` in `src/core.jsx`).
- Consumers that have a year use `sectorsForYear`: the `result/` page
  (payload `year` from `ResultState.decode`), the Worker completion email
  (Green-Up Plan; `body.year`), and the Worker `/api/city` stats
  (`opportunities`/`strengths`; use the season `maxYear` already computed
  there). Investigate each call site before editing; if a consumer
  genuinely has no year (live gameplay), it keeps `SECTORS`. Do not thread a
  year through places that do not already have one.
- `result-state.js`: check whether decode validates fills against the
  current `SECTORS` shape; if so, validate against `sectorsForYear(year)`.
- Tests: `bun test` cases for `sectorsForYear` (exact, fallback-down,
  before-earliest) and one asserting `SECTORS === sectorsForYear(CURRENT_YEAR)`.
- Docs: a short "Adding a new season's questions" paragraph in

## Task 3: Nightly sheet backup (Worker cron, emailed via Resend)

- `wrangler.jsonc`: add `"triggers": { "crons": ["0 10 * * *"] }` (daily
  10:00 UTC).
- `worker/index.js`: add a `scheduled(event, env, ctx)` export. It reuses the
  existing sheet-read path that `/api/city` already uses (find it; do not
  duplicate the fetch logic), builds a CSV of every row and every field the
  read path returns (header row from the union of keys; RFC 4180 quoting;
  nested objects such as the answers blob JSON-stringified into the cell),
  and sends it through the existing Resend send path as an attachment
  (`attachments: [{ filename, content: <base64> }]`) to the address in a new
  secret `BACKUP_EMAIL`, subject `Green Radius backup <YYYY-MM-DD> (<N> rows)`,
  filename `green-radius-<YYYY-MM-DD>.csv`. Missing `BACKUP_EMAIL`,
  `RESEND_API_KEY`, or sheet secrets: log a structured event
  (`type: "backup_skipped"` with a `reason`) and return; never throw. Success
  and failure log `backup_sent` / `backup_failed` with the row count,
  following the file's existing structured-log style.
- Tests: `bun test` cases via the existing `withMockFetch` helper: happy path
  (Resend called once with an attachment whose decoded CSV has the header
  and N rows), missing `BACKUP_EMAIL` (no fetch to Resend), sheet read
  failure (`backup_failed`, no Resend call).
- Docs: `.dev.vars.example` gains `BACKUP_EMAIL=` (name only);
  `docs/architecture.md` gets the cron in its Worker route list and a short
  "Backups" note; `docs/admin-setup.md` secret list gains `BACKUP_EMAIL`
  with the one-line `npx wrangler secret put BACKUP_EMAIL` instruction;
  `CLAUDE.md`'s "One Worker, eight dynamic routes" bullet mentions the cron.
- Local check: `npx wrangler dev --test-scheduled` then
  `curl "http://localhost:8787/__scheduled?cron=0+10+*+*+*"` is the documented
  way to fire a cron locally; if `.dev.vars` is absent, the skipped path is
  what you will see, which is fine. See the memory note at

## Task 5: Surface and retry failed submits; resend or fix the email

- Done screen (`green-radius.jsx`). Trace the existing submit flow first:

  the R4 nonce is generated and stored, and how the Apps Script `doPost`
  dedupes on it (`docs/apps-script/Code.gs`). Write what you found at the
  top of your report before changing code.
- Behaviour:
  1. If the POST fails (network/5xx) or the response has `sheet: false`:
     show a gentle inline state "Your result didn't go through. Tap to try
     again." with a Retry button that re-POSTs the same body with the same
     nonce. Disable the button while in flight. Success clears the state.
  2. If `sheet: true` but `email: false`, or after any successful submit:
     show "Didn't get the email? Resend it, or fix your address." with the
     email shown in an editable input and a Resend button. Resend re-POSTs
     with the same nonce and the (possibly corrected) email. Note in the
     report what the sheet does with a same-nonce, different-email replay
     (dedupe rejects the second row is expected and acceptable; the email
     leg is what matters here); if the Worker or Apps Script would treat a
     dedupe as failure and report `sheet: false`, make the UI treat
     "already recorded" as success for the retry path (check what the
     Worker actually returns for a dedupe before deciding).
  3. Fire `trackEvent('submit_retry')` and `trackEvent('email_resend')` via
     `trackEvent` from `src/core.jsx` (never `window.sendEvent`).
